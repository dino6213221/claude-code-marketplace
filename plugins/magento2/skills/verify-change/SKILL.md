# Change verification (QA)

You verify a change on the **local** environment. Never staging/production unless the user explicitly names that environment. Every check result has evidence. Scope: $ARGUMENTS (or whatever the user / orchestrator pointed to).

## 0. Mode and environment

**Mode:**
- **Pipeline** — you are invoked by the `delivery:qa` agent (`var/agents/.current` and the issue's `03-test-plan.md` exist). Take the cases from the test plan, record results in `06-qa.md`, `<KEY>` = issue key.
- **Standalone** — everything else. Derive the cases yourself from the change description / ACs / `git diff` (show the list to the user before executing), report the result in the chat (format in section 5). `<KEY>` = Jira key from the branch or the request; without one — a short slug, e.g. `QA-cart-badge-`.

**Environment** (`<URL>`, `<EXEC>`, `<DB>`, frontend):
1. `CLAUDE.md` contains the "Local environment" section (generated by `/delivery:init`) → take the values from there.
2. Otherwise run `magento2-detect "$CLAUDE_PROJECT_DIR"` (command from the `magento2` plugin) and use:

   | `ENV_TOOL` | `<EXEC>` | `<DB>` |
   |---|---|---|
   | `warden` | `warden env exec -T php-fpm` | `warden db connect` |
   | `reward` | `reward env exec -T php-fpm` | `reward db connect` |
   | `ddev` | `ddev exec` | `ddev mysql` |

   `<URL>` = `BASE_URL`. Missing or several candidates → ask the user. State the values you use in one sentence and carry on.
3. Environment not running (`<EXEC> php -v` fails) → stop and tell the user; do not start the environment yourself without approval.

## 1. Choosing the method — for each test case

| What the issue changes | Method | Browser? |
|---|---|---|
| `.phtml` templates, layout XML, CSS/JS, Alpine/Knockout, PWA components | rendering + interaction | **yes** |
| Checkout, cart, customer account, forms | user flow | **yes** |
| Admin: forms, grids, configuration, ACL visible in the UI | admin flow | **yes** |
| Transactional e-mails | trigger + environment webmail | **yes** (webmail) |
| GraphQL resolver / REST endpoint | `curl` to `<URL>/graphql` or `/rest/...` | no (for PWA also the browser, if the AC concerns the UI) |
| Cron, queue consumer, CLI command, import | `<EXEC> bin/magento ...`, logs, DB read | no |
| Observers/plugins without UI | trigger the action (CLI/API/UI) + read the effect in DB/log | depends on the trigger |
| Indexes, cache, FPC | flush/reindex + compare responses (`X-Magento-Cache-*` headers) | optional |

Rule: browser when the AC describes something a **person sees or clicks**. Otherwise the cheapest deterministic method. When both — both.

**Proportionality:** test as much as the change can break, no more. A simple change (one template, one resolver, one config value) → check the ACs and, for a bug, the original reproduction; skip mobile, FPC, other store views and extra regression unless the change touches them. One piece of evidence per case is enough.

## 2. Preparation
1. Deployment steps: in the pipeline from `04-implementation.md`; standalone — derived from the diff (new `db_schema.xml`/patch → `setup:upgrade`, `di.xml` → `cache:flush`, always `cache:flush` before testing). Show state-changing commands before running them.
2. Note the log line counts (`<EXEC> wc -l var/log/exception.log var/log/system.log`) so that after the test you report only new entries.
3. Dummy data: synthetic only, prefix `QA-<KEY>-`, e-mails at `example.com`, created through the Magento API/CLI. Every record goes straight into the "Dummy data" table (pipeline: `06-qa.md`; standalone: the report). No DROP/TRUNCATE/ALTER, no DELETE/UPDATE without WHERE and no raw SQL writes to records other than dummy data — outside the pipeline no hook enforces this.

## 3. Browser (Playwright MCP from the `magento2` plugin)
Tools: `mcp__plugin_magento2_playwright__*`. Common ones: `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_fill_form`, `browser_select_option`, `browser_wait_for`, `browser_console_messages`, `browser_network_requests`, `browser_take_screenshot`, `browser_resize`, `browser_tabs`, `browser_close`.

For each case:
1. `browser_navigate` to `<URL>` (local certificates are accepted — the server runs with `--ignore-https-errors`).
2. `browser_snapshot` before interacting — click by snapshot references, not guessed selectors.
3. Execute the steps. After every action that loads data (AJAX, GraphQL in PWA), `browser_wait_for` the expected text/element.
4. Check:
   - the expected result (text, state, price, message),
   - `browser_console_messages` — JS errors = defect, unless they existed before the change (check a page without the change),
   - `browser_network_requests` — 4xx/5xx responses and errors in GraphQL responses (`errors` in the JSON),
   - mobile view only if the change affects layout/responsive behavior: `browser_resize` 375×812, then back to 1440×900.
5. Evidence: `browser_take_screenshot` named `<case-ID>-<step>.png`; record the file path returned by the tool next to the result. A screenshot must not show personal data or real orders — dummy data only.
6. FPC: only if the change affects cacheable output (blocks, layout, cache tags) — check the result after `cache:flush` and on the second visit (page from cache).

### Logging in
- **Admin:** never type the password through the tools or save it in files. Open `/<admin-path>` in the Playwright browser and ask the user to log in manually in the opened window; the session stays in the browser profile while you work. Get the admin path from `<EXEC> bin/magento info:adminuri`.
- **Storefront customer:** a dummy account `QA-<KEY>-...@example.com` created through the API/CLI. Generate the password randomly in the session, never save it in handoff files or Jira; delete the account with the rest of the dummy data after the test.

### When the browser does not work
The Playwright server does not start (no `npx`/browser) or the page does not respond → do not guess the result. Mark the case "NOT RUN — <reason>", add a question to "Open questions" (standalone: tell the user) and, in the pipeline, finish with status FAIL (the "all cases executed" criterion is not met).

## 4. Without the browser
- GraphQL: `curl -sk -X POST <URL>/graphql -H 'Content-Type: application/json' -d '{"query":"..."}'`. For store-specific queries add the `Store: <code>` header. Check `data` and the absence of `errors`.
- REST: `curl -sk <URL>/rest/<store>/V1/...`; tokens only via `op read` or from the user — never typed into the command in plain text.
- CLI/cron: `<EXEC> bin/magento cron:run --group=<group>` or the module's command; read the effect with `<DB> -e "SELECT ... WHERE ... LIKE 'QA-<KEY>-%'"`.
- Summarize DB results (counts, dummy data IDs); never paste raw rows.

## 5. After the test
- New entries in `var/log/exception.log` / `system.log` since the noted line → for each case: "none" or a summary (exception class, message without personal data).
- Case result: PASS / FAIL / NOT RUN, with evidence (screenshot file, summarized API response, command + output).
- Defect: steps to reproduce, expected, actual, severity (Critical / High / Low), evidence.
- Close the browser tab (`browser_close`) at the end of the round.

### Standalone report
```
Environment: <ENV> · <URL> · frontend: <...>
| ID | What was checked | Method | Result | Evidence | Notes |
Defects: | ID | Steps to reproduce | Expected | Actual | Severity |
New log entries: none | <summary>
Dummy data: | Type | Identifier | Store |
```
Keep it short: one row per case, one-line notes, prose only for defects; omit empty sections.
At the end ask whether to delete the dummy data; delete only records from the table, by ID/prefix. In the pipeline the orchestrator orders the cleanup.
