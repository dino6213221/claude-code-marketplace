You prepare the current project for the `/delivery:deliver` pipeline. A plugin cannot install project settings by itself, so you generate them from the plugin's templates for the detected environment.

Tools and files:
- `magento2-detect` — command from the `magento2` plugin (on PATH because `delivery` depends on it); detects the project layout and prints `KEY=VALUE`
- `${CLAUDE_PLUGIN_ROOT}/scripts/render.sh` — generates `settings.json`, the `CLAUDE.md` section and `retired-rules.json` from `.claude/delivery.json`
- `${CLAUDE_PLUGIN_ROOT}/templates/gitignore-snippet` — `.gitignore` entries
- `${CLAUDE_PLUGIN_ROOT}/templates/legacy-headings.txt` — headings of `CLAUDE.md` sections generated by versions before 1.1.0 (no markers)

## Rules
- Never overwrite anything wholesale. Read every target file first, then show the user the planned change (diff) and wait for approval, separately for each file.
- Do not remove existing rules, entries or sections (exceptions: your own generated `CLAUDE.md` section — step 6 — and retired rules the user approves — step 5).
- Do not read `app/etc/env.php`, `auth.json` or secret values from `.env`. Do not commit. Do not `cd` — use absolute paths.
- Keep working files in the session's temporary directory, not in the repo.

## Steps
1. **Project directory**: `$CLAUDE_PROJECT_DIR` (or the session's working directory). Confirm it with the user.
2. **Detection**: `magento2-detect "<project directory>"`. Command not found → the `magento2` plugin is disabled; ask for `/plugin install magento2@daniel-marketplace`.
   Show the result as a table and collect missing or ambiguous values:
   - `MAGENTO_ROOT` empty → ask (directory containing `bin/magento`, relative to the project),
   - `ENV_CANDIDATES` lists several tools or `ENV_TOOL` is empty → ask which environment is used: `warden` | `reward` | `ddev` (fixed prefixes), `custom` (any other setup — docker compose, docker-magento, VM: ask for `exec` = the command prefix that runs PHP in the Magento directory, `db` = the database client command, optional `envName`, `extraDeny` for the setup's destructive commands such as removing volumes) or `native` (PHP on the host; only when `magentoRoot` is `.`, otherwise `custom`),
   - `EDITION` (`adobe-commerce` | `open-source` | `mage-os`) and `MSI` (`yes`/`no` → `msi: true/false`) → confirm; empty → leave unset (agents check when needed),
   - several websites / store views? → `multiStore: true/false`; if the environment is running, `<EXEC> bin/magento store:list` answers it; unknown → leave unset,
   - `FRONTEND` empty or uncertain → ask (`hyva`, `luma`, `pwa`; several allowed),
   - `BASE_URL`, `MAIL_URL`, `PHP_CONSTRAINT` empty → propose a value or leave it empty (agents will ask when needed),
   - `VCS_HOST` / `VCS_REPO` → confirm (`github` | `bitbucket` | `gitlab` | `other`),
   - language of the handoff prose (headings stay English) → ask; default: the language the user writes in,
   - known environment workarounds (e.g. how phpunit or phpcs must be started in this project) → ask; each becomes one line in `CLAUDE.md`, and a command the reviewer/developer must run becomes an `extraAllow` rule (show it, approve separately).
3. **Configuration**: write `.claude/delivery.json` (show it before writing):
   ```json
   {
     "magentoRoot": ".",
     "env": "ddev",
     "baseUrl": "https://shop.ddev.site/",
     "mailUrl": "https://shop.ddev.site:8026/",
     "edition": "open-source",
     "msi": true,
     "multiStore": false,
     "frontend": ["hyva"],
     "php": "~8.3.0",
     "language": "English",
     "vcsHost": "github",
     "vcsRepo": "org/shop",
     "envWorkarounds": [],
     "extraAllow": []
   }
   ```
   Only `magentoRoot` and `env` are required; leave unknown keys out (the generated section then tells agents to check). `custom` additionally needs `exec` and `db`, e.g. `"exec": "docker compose exec -T php", "db": "docker compose exec -T db mysql magento"`. `envWorkarounds` are one-line notes about how this project's tools must be started (e.g. a phpunit bootstrap option, a phpcs `installed_paths` setting), `{{EXEC}}` is replaced with the prefix. `extraAllow` / `extraDeny` are extra permission rules for exactly those commands.
   No secrets in this file — it may be committed if the team uses the same environment. `extraAllow` rules must be read-only or test commands; never a rule that writes data, pushes, or reads secret files. If the file already exists, show the differences and ask which values to change.
4. **Generation**: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/render.sh" "<project>/.claude/delivery.json" "<temporary directory>"`.
5. **`.claude/settings.json`**:
   - no file → create it from the generated one,
   - file exists → merge: `env` (keys only when missing), `permissions.allow|deny|ask` (union without duplicates), `permissions.defaultMode` only when missing. Other project keys unchanged. You may use `jq -s`.
   - Retired rules: every rule from the generated `<temporary directory>/retired-rules.json` found in the same list of the project's settings (e.g. the old `allow: Bash(<EXEC> tail *)`, which let agents read `app/etc/env.php`) → show them and, with approval, remove them.
   - Conflict (the same rule in `allow` and `deny`, or rules of the previous environment after an `env` change) → show it and ask.
6. **`CLAUDE.md`** in the project directory — the generated section is wrapped in `<!-- delivery:begin … -->` / `<!-- delivery:end -->`:
   - markers present → show the diff and, with approval, replace everything between them (markers included),
   - no markers but a section starting with a heading from `legacy-headings.txt` (e.g. the Polish `# Kontekst projektu (wspólny dla wszystkich agentów)` from 1.0.x) → it is a section generated by an older init: show the diff and, with approval, replace it (up to the next first-level `# ` heading or the end of the file) with the marked section. Never keep both — two sections give agents contradictory rules (e.g. Polish vs English handoff headings),
   - nothing found → append the generated section at the end of the file (or create the file).
7. **`.gitignore`**: append missing lines from `gitignore-snippet`. Check that the handoff directory is ignored: `git check-ignore -q "<magentoRoot>/var/agents/x"`; if not — append `<magentoRoot>/var/agents/`.
8. **Leftovers check**: `find "<project>/<magentoRoot>/var/agents" -type d -name .claude` — agent memory written under a handoff directory (caused by a changed working directory). Found → propose moving its contents into `<project>/.claude/agent-memory-local/` (with approval), otherwise it is lost at closing.
9. **Environment check** (if the containers are running; if not — skip and report):
   - `<EXEC> php -v` and `<EXEC> ls bin/magento` (native: without a prefix) — confirms the command prefix and the working directory; error → show it and ask for the correct prefix,
   - `<DB> -e "SELECT 1"` — confirms the database command,
   - every `envWorkarounds` command that is cheap to run (e.g. phpunit on one small test) → run it once to confirm it works,
   - `HAS_JQ=no` → pipeline hooks do not fully work (`brew install jq`),
   - `HAS_NPX=no` → the Playwright server from the `magento2` plugin (browser QA) will not start; Node.js is required,
   - Atlassian: the `workflow` plugin's server (`https://mcp.atlassian.com/v2/mcp`) needs a one-time OAuth login — ask the user to run `/mcp`, pick `plugin:workflow:atlassian` and authenticate; then check with `atlassianUserInfo`. If the user also has Atlassian from another source (project `.mcp.json` server `atlassian`, claude.ai connector, the `atlassian` plugin), tell them the pipeline ignores it and they may disable it to avoid duplicate tools.
10. **Summary**: what changed in each file, what was skipped and why. Projects with `.claude/delivery.json` committed: tell the user that `extraAllow`/`envWorkarounds` then apply to the whole team. Remind the user to run `/reload-plugins` or restart the session so the permissions and `CLAUDE.md` take effect.
