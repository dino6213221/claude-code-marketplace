# Jira comments

Readers are people outside the code (reporter, PM, tester, deployer), often on a phone. A comment is good when they can answer or act after reading it once — and when it reads like a message from a colleague, not from a system.

## Rules
1. **Human tone.** Write the way a colleague writes to a colleague: full, natural sentences, "we" for the team and "you" for the reader, a polite ask ("Could you confirm…", "Can you check…"). Address the person by name when one person has to answer ("Anna, …"). When replying to someone's answer, a short thanks is fine ("Thanks, that settles it."). No telegraphic style (fragments, arrows, abbreviations, labels like "Decision needed:" or "Status:"), no bureaucratic or machine phrasing ("Please be advised", "The following items require attention"), no impersonal passive where "we" works.
2. **First line = the ask or the fact**, said to the person — not background, not a long greeting: "Anna, before we start we need two decisions from you:" / "We fixed it in the PR below; after the deploy one manual step is needed."
3. **Short.** At most 600 characters and 8 lines, not counting the manual-actions list. Longer → cut, never split into several comments. At most 5 questions.
4. **One purpose per comment** — one of the types below. Do not restate the description or the acceptance criteria; refer to them ("AC2 in the description") only when the issue itself numbers them, otherwise quote at most 10 words.
5. **Language of the issue's discussion** (the latest human comments; none → the description). Established terms stay as they are (deploy, cache, checkout). No calques.
6. **Reader vocabulary.** Describe behavior the reader sees, not the implementation: no class, file, table or column names, SQL, stack traces, log excerpts, commit hashes. No pipeline internals: handoff files, agent names, stages, tracks, sizes, risk flags, statistics.
7. **Data.** No customer data, raw database rows or logs. Counts instead of lists ("338 products"). Product identifiers only when the reporter used them or a tester needs them to reproduce — at most 3.
8. **Format.** Plain sentences. A numbered list only for questions, options, proposed issues or manual actions. No headings, bold labels, tables, emoji, formal greetings ("Hello team,", "Dear …"), sign-offs, signatures or "generated by" lines.
9. **People.** Name who has to answer. An @mention notifies — use it only when the user approves it.
10. **Publishing.** Show the user the exact text; post exactly the approved text. Never edit or delete other people's comments; edit an own comment only with approval.

## Types
**Questions** (work is blocked) — first line says to the person what we need from them and why we wait. Numbered questions, each answerable with yes/no or a choice between named options, each with the answer we would assume, said plainly: `(we would assume yes)`. Only questions no system can answer — data that can be read from an environment is checked, not asked.

**Scope confirmation** (only when the agreed scope differs from the description) — 1–3 sentences: what will be done, what will not.

**Split proposal** — "Proposal: split into N issues:" then one line per issue: `<title> — <scope in at most 12 words>`.

**Delivery note** (code done) — 1–2 sentences on what changed for the user ("Products on catalog price rules now show…"), one line on how to verify it, the PR link (or branch name). Then either the line "Deploy: code only." or "Manual actions after deploy:" with the numbered list of exact commands / click paths, copied verbatim from the deployment steps (exempt from the length limit, never summarized; commands in a code block).

## Examples
Good — questions:
```
Anna, before we start we need two decisions from you:
1. If a product has been on promotion since it was created, should we show the promotional price as the lowest price from the last 30 days? (we would assume yes)
2. If the discount grows during a promotion (from -20% to -25%), should we count the 30 days from the first discount? (we would assume yes)
```

Good — delivery note:
```
Products on catalog price rules now show the lowest price from the last 30 days, also when the rule started before the product was created. You can check it on the product page of any promoted product, in the "lowest price" line. PR: <link>
Manual actions after deploy:
1. Production, CLI — `bin/magento omnibus:history:rebuild` — once — history filled for all promoted products
```

Bad — one paragraph restating every acceptance criterion, with table names, product IDs and an out-of-scope list: the reader cannot find the question, and it repeats the description.

Bad — telegraphic, reads like a log:
```
Decision needed. Q1: promo since creation → lowest = promo? Q2: step discount → window from 1st? Default: yes/yes.
```
